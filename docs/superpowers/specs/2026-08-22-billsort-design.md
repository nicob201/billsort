# billsort — design spec

Date: 2026-08-22
Status: approved (design), pending implementation plan

## Purpose

`billsort` is a Go CLI that automates a recurring manual chore: organizing tax and
utility documents (facturas + comprobantes de pago) for three family houses into a
pre-existing Google Drive folder structure. Secondary goal: a first real Go project,
and a learning vehicle for AI-assisted document extraction (Gemini API).

Not a hosted service, not multi-user — a personal tool run manually, roughly monthly,
by one person.

## Scope (v1)

**In scope:**
- 4 houses, each with its own set of categories:
  - Igarzabal, Pardos y Morenos, Yaco Misque → Agua, Gas, Luz
  - La Granja → Agua, Luz only (no Gas service at this house)
- Both documents per bill: factura (the bill) and comprobante de pago (payment receipt)
- PDF, JPG, JPEG, PNG input files
- Uploading to Google Drive with the existing folder/naming convention preserved
- Creating the `/año/` folder automatically when a new year starts

**Explicitly out of scope for v1** (revisit later, not blockers):
- **Rentas** — paid annually per house, not monthly; excluded from automated
  handling entirely (no renaming, no matching, no upload via this tool).
- **Fiat Toro** (vehicle documents) — existing filenames are inconsistent
  (mismatched pairs, varying formats: "rentas toro" vs "rentas y municipal Toro").
  Will be mapped in a future iteration once the core 3-houses flow is proven.

## Existing Drive structure (must be preserved)

```
/<año>/<nombre-de-la-casa>/<categoría>/
```

Example: `/2026/Igarzabal/Agua/`

## Filename convention (must be preserved)

```
NN-<número de factura tal cual lo imprime la empresa>[ pago].<ext>
```

Examples observed in the existing Drive data:
- Agua: `03-FC-0010-71103571.pdf` (factura) + `03-FC-0010-71103571 pago.pdf` (pago)
- Gas: `05-0400B71710540A.pdf` + `05-0400B71710540A pago.jpeg`
- Luz: `05-0007 - 06055055.pdf` + `05-0007 - 06055055 pago.jpeg`

Rules:
- `NN` is a **simple, zero-padded load counter** — "the Nth pair added to this
  folder" — confirmed with the user, not tied to calendar month/bimester. Computed
  as: **the highest `NN` currently present in the target Drive folder, plus 1**
  (not a plain count — La Granja's existing files have gaps, e.g. `02` then `06`
  with nothing in between, so counting entries would collide; max-plus-one is
  gap-safe and works for every house).
- The invoice number segment is copied verbatim from what the AI extracts off the
  document (it is the utility company's own printed reference — not generated by
  this tool).
- `" pago"` (literal, space + pago) is appended to the base name — same as the
  factura's base name — only for the payment receipt.
- File extension is preserved as-is from the input file (pdf/jpg/jpeg/png); no
  format conversion.

**La Granja note:** its existing Drive files don't follow this convention today
(e.g. `02-2026 agua la granja.pdf`, `06-agua granja.pdf` — a descriptive name
instead of the real invoice number, inconsistent use of the year, gaps in `NN`).
Confirmed the invoice number and account number both exist on La Granja's bills
just like the other houses — the tool applies the standard convention to it
**going forward only**. Retroactively renaming La Granja's already-uploaded files
to match is out of scope for v1 (see Out of scope).

## House identification

Each factura carries a **fixed client/account number** (distinct from the invoice
number, which changes every bill) that uniquely identifies the house for that
category. The user supplies these numbers once, in a local config file — **not
hardcoded in source, not committed** (see Secrets below). 11 numbers total: 3
houses × 3 categories (Igarzabal, Pardos y Morenos, Yaco Misque) + La Granja × 2
categories (Agua, Luz — no Gas).

Do not attempt address-text matching — it was considered and rejected in favor of
the account-number lookup, which is unambiguous.

## Factura ↔ pago matching

Confirmed behavior (from direct user input, not assumption):

- Facturas and their payment receipts usually arrive in **separate runs** — the
  factura first, the comprobante de pago days or weeks later, once paid.
- It is normal to have **more than one pending (unpaid) factura at once** for the
  same house/category (e.g. current month's bill uploaded before it's paid, next
  month's bill already arrives too).
- The comprobante de pago does **not** reliably show the original invoice number
  (confirmed by user — varies by payment method, but assume it's absent). Matching
  must use: **casa + categoría + monto**.

Matching algorithm when a "pago" document is classified:
1. List existing facturas in the target Drive folder that don't yet have a paired
   "pago" file.
2. Filter by **exact amount match** (no tolerance in v1 — these are utility
   payments with no fees expected; revisit only if real usage shows false
   negatives from rounding).
3. **Exactly one match** → pair it: reuse that factura's `NN`, upload as
   `NN-<numero_factura> pago.<ext>`.
4. **Zero or multiple matches** → do not guess. Prompt the user interactively in
   the terminal, listing the candidate(s) (or the lack thereof), and let them pick
   or skip.

## CLI flow (single command, `billsort process <local-folder>`)

1. Read all files in the given local folder (flat — houses/categories are mixed
   together; classification determines routing, the user does not pre-sort).
2. For each file, call Gemini with a structured-extraction prompt requesting JSON:
   `{numero_cuenta, categoria, tipo: "factura"|"pago", monto, numero_factura?,
   confianza}`.
3. Map `numero_cuenta` → house name via the static config table.
4. Determine action per file (new factura upload vs. pago needing a match — see
   above) and the computed target filename + Drive path.
5. Print a dry-run summary table: local file → planned action → Drive destination.
6. Single confirmation prompt (y/n) before any upload happens.
7. On confirm: create the `/año/` folder if it doesn't exist yet, then upload each
   file with its computed name to its computed folder.
8. Print a final report, including which facturas remain unpaid (no matching pago
   yet) — this is a genuine secondary benefit: a pending-payments view.

No local database or cache — the tool is stateless and re-reads the live Drive
folder contents on every run. Rejected a local index (SQLite/JSON) as unnecessary
complexity for ~20-25 files/month; listing a Drive folder via API is cheap and
avoids any risk of local state drifting from what's actually in Drive.

## Error handling

- **Low-confidence or incomplete extraction** (Gemini can't confidently determine
  a required field): do not guess — flag the file as "needs manual review", skip
  it from the upload plan, list it in the final report.
- **Name collision**: if the computed target filename already exists in the Drive
  folder (e.g. the same batch run twice by accident), warn and skip — never
  silently overwrite.
- **Drive/Gemini API errors** (auth expired, network): fail fast with a clear
  message; do not partially upload a batch without telling the user what
  succeeded and what didn't.
- **Ambiguous pago match**: interactive prompt, as described above — never a
  silent guess on a financial record.

## Secrets & config (repo is public)

None of the following are ever committed — all gitignored, with an example
template checked in instead:

- `houses.yaml` (real) / `houses.example.yaml` (template, committed) — the 11
  account-number → house/category mappings. Structure must allow a house to
  list only the categories it actually has (La Granja: Agua + Luz only, no
  Gas) rather than assuming every house has all 3.
- Google OAuth client credentials + cached token for the Drive API
  (`drive.file` scope only — minimal access, limited to files this app creates).
- Gemini API key (env var).

## Project layout

```
billsort/
├── main.go                  # entry point, flag parsing
├── go.mod
├── internal/
│   ├── classify/             # Gemini client + extraction prompt/schema
│   ├── drive/                 # Drive API: list, upload, folder create/find
│   ├── match/                  # NN computation + factura/pago pairing (pure logic)
│   └── config/                  # loads houses.yaml
├── houses.example.yaml
└── .gitignore
```

`match` has no network dependency and is unit-tested with the stdlib `testing`
package (table-driven tests). `classify` and `drive` sit behind small interfaces
so `match`'s logic (NN counting, amount-based pairing, ambiguity detection) is
testable without hitting live APIs.

## Explicitly rejected alternatives

- **Local SQLite/JSON index of Drive state** — adds a state-sync-drift risk for
  no real benefit at this volume (~20-25 files/month); the stateless
  list-Drive-live-every-run approach was chosen instead.
- **Per-file interactive confirmation** — defeats the purpose of automating a
  tedious manual process; replaced with a single dry-run summary + one
  confirmation before any upload.
- **Address-text matching for house identification** — less reliable than the
  fixed account-number lookup table; rejected.

## Out of scope / future work

- Rentas category (annual payment, different document shape — no factura/pago
  pairing today).
- Fiat Toro (vehicle) documents — inconsistent existing naming, needs its own
  mapping pass.
- Retroactively renaming La Granja's already-uploaded files to match the
  standard convention (v1 only normalizes new uploads going forward).
- Due-date reminders / Calendar integration (raised in earlier discussion, not
  part of this v1).
